# 关键设计取舍 · Design Trade-offs

**项目：** 糖尿病足检查助手（FootCheck）
**版本：** v3.16 ｜ **日期：** 2026-10-14

本文说明本项目几个**刻意的、可能反直觉**的设计决定，以及它们的理由与代价。核心原则只有一条：**在临床安全问题上，宁可保守、可解释、可审计，也不追求"聪明"。**

---

## 1. 为什么用确定性规则，而不是大模型盲判？

**决定：** 就医层级（EMERGENCY / PRIMARY_CARE / SELF_CARE / ABSTAIN）、风险等级、IWGDF 分级，**全部由确定性规则引擎产出**；不使用大模型做最终判定。

**理由：**

1. **可审计。** 每条规则都写明来源与出处（IWGDF 2023、NICE NG19、IWGDF/IDSA 2023、SIRS、Sepsis‑3），可逐条对照公开指南。大模型的判定无法给出稳定的、可复现的依据。
2. **可复现。** 同一组作答**永远**得到同一结果（`test:crosslang` 还验证了跨语言一致）。大模型的输出存在随机性，临床分诊不能"每次略有不同"。
3. **红旗不能靠"猜"。** 急症触发规则是简单的模式匹配：`IF 坏疽 THEN EMERGENCY`。这类判断**必须确定**，不能交给概率模型。
4. **保守优先。** 规则在不确定时**向上分级**（`ABSTAIN` 建议就医），而不是向下安慰用户。

**代价（如实说明）：** 规则引擎只覆盖**结构化问题**，无法理解自由文本描述；表达多样性、口语化描述会落到"不明确"，从而触发保守的 `ABSTAIN`。这是**有意的取舍**——宁可多建议就医，也不漏掉红旗。

> 语言模型在本项目中**至多**用于解释与教育文案，**永远不能修改**规则引擎给出的层级。

## 2. 为什么聚焦 5 种语言，且不做 AI 图像诊断？

### 2.1 聚焦 5 种语言（en / zh-CN / ms / ta / fil）

**理由：**

- **匹配目标人群。** 项目面向新加坡 60 岁以上糖尿病患者，这 5 种语言覆盖当地主要语言群体（英语、华语、马来语、泰米尔语、菲律宾语）。
- **临床安全要求完整覆盖。** 红旗症状、就医建议、免责声明**必须在每种语言里都完整**，否则非英语用户可能拿到更差的分级。因此我们对 5 种语言做**完整翻译 + 逐 key 对齐校验**（`npm run test:i18n-keys`：0 缺失 / 0 孤儿），并新增**跨语言一致性测试**（`test:crosslang`：同一组作答在 5 种语言下分级完全一致）。
- **语言与逻辑解耦。** 引擎只产出**翻译 key**，UI 层按语言渲染，因此**新增语言不影响临床逻辑**。

**翻译说明：** 5 种语言的词条由 AI 从英文基线翻译而来，并做了自动化一致性校验（key 对齐、占位符、空值检查）。**尚未经逐条人工母语审校**——这是已知局限（见第 5 节）。

### 2.2 不做 AI 图像诊断

**理由：**

- **证据与合规。** 用照片自动判断伤口/坏疽属于**医疗器械级别**的功能，需要监管审批与临床验证，超出本演示工具范围。
- **假阴性风险高。** 图像模型漏判一个坏疽的代价极高；而**让用户自己回答结构化问题 + 明确提示"看到这些就立刻就医"**更安全、更可解释。
- **可及性。** 老年用户拍摄清晰、光线一致的足部照片并不容易；结构化问卷 + 文字教育更稳妥。
- **诚实定位。** 本项目定位为**筛查/教育工具**，不是诊断设备。加一个"AI 看图诊断"会破坏这一定位。

## 3. 数据隐私与 PDPA 考虑

| 关注点 | 做法 |
| --- | --- |
| 数据最小化 | 只采集评估所需字段；不采集姓名、NRIC、电话等身份信息 |
| 本地优先 | 个人资料、评估历史、每日打卡**只存浏览器 localStorage** |
| 不跨境 | 默认**不上传**任何用户数据到服务器 |
| 无第三方追踪 | 产物中**不含**分析/广告 SDK |
| 可删除 | 用户清除浏览器数据即删除全部本地记录 |

设计上把**数据留在用户设备**，直接规避了大部分 PDPA 的收集、跨境与留存义务。

## 4. 为什么演示版不上传数据到服务器？

**决定：** 演示版**不把用户数据上传到任何服务器**（CloudBase 路径 `cloudEnabled = false`）。

**理由：**

1. **零服务端信任边界。** 没有服务端，就没有"服务端被攻破"的风险面；用户数据不离开设备。
2. **演示无需登录。** 无需注册即可试用，降低使用门槛，也避免采集账户数据。
3. **云端资源不稳定。** 本环境尝试开通云端返回 `cancelled` / `cloud_service_unavailable`，因此按"可选增强"处理：云端可用才写云，失败自动落回本地，**绝不阻塞主流程**。
4. **可平滑升级。** 生产阶段若确需云端（如多设备同步），`cloudDb.ts` + `cloud/schema.sql` 已按"**公共演示表 / 无登录 / 仅合成数据**"准备好：字段白名单 + 长度限制 + RLS，且前端只持有 publishable key（无管理员密钥）。届时只需填入 `publicConfig` 即可接通，**无需改动临床逻辑**。

**代价：** 数据**不跨设备同步**——换浏览器/清缓存即丢失。对演示场景可接受。

## 5. 已知局限（Known Limitations）

1. **不是临床验证。** 测试全部是**回归测试**（确保代码行为稳定、分级可复现），**不是**临床试验或医学验证，**不能**证明临床有效性。
2. **翻译未经逐条人工审校。** ms / ta / fil 由 AI 翻译 + 自动校验，医学/口语术语建议母语者复核。
3. **SIRS 仅采集部分项。** 工具只采集 4 项 SIRS 标准中的**体温**（经红旗问题）；心率、呼吸、白细胞需临床测量，超出本工具范围（已在代码注释说明）。
4. **规则覆盖结构化问题。** 无法理解自由文本；表达不清会触发保守的 `ABSTAIN`。
5. **人群与地区局限。** 面向新加坡 60+ 已确诊糖尿病人群；内置护理机构与人群统计为新加坡数据。
6. **云端未接通。** 无跨设备同步，无服务端留存。
7. **不做用药建议。** 输出仅限就医层级与自我护理教育，**不提供任何药物或剂量建议**。
8. **数据源为公开/内置。** 唯一外部依赖是公开免密钥的 `data.gov.sg`；失败时回退内置数据，可能不是最新。

---

## 6. 一句话总结

> 我们选择**确定性、可解释、本地优先、保守分级**：规则引擎做判定（可审计、可复现），大模型不参与判定；数据留在用户设备；不确定时宁可建议就医。这些取舍牺牲了"智能感"与"跨设备同步"，换来**临床安全性与隐私**——对老年糖尿病人群的足部筛查，这是正确的方向。
