# 糖尿病足检查助手 — 技术规划文档

> **状态：** 规划阶段（暂不编写代码、不创建数据库、不部署）  
> **目标用户：** 60 岁及以上、已确诊 1 型或 2 型糖尿病的成年人  
> **支持语言：** English, 简体中文, Malay, Tamil, Filipino  
> **后端：** 腾讯云开发（CloudBase / TCB）  
> **源代码管理：** GitHub（单体仓库）

---

## 0. 目标人群（Target Population）

| 维度         | 定义                                              |
| ---------- | ----------------------------------------------- |
| **年龄**     | **60 岁及以上**                                     |
| **疾病**     | **已确诊的 1 型或 2 型糖尿病**（不含妊娠糖尿病、糖尿病前期）             |
| **年龄分段**   | 60–69 · 70–79 · 80–89 · 大于 89                   |
| **不覆盖**    | 60 岁以下人群；未确诊糖尿病者；妊娠糖尿病；糖尿病前期                    |
| **使用场景**   | 居家足部自查 → 就医导航（筛查与教育工具，**不做诊断、不给用药建议**）          |

**为什么聚焦 60 岁及以上？** 糖尿病足溃疡与截肢风险随年龄显著上升。老年糖尿病患者常同时存在周围神经病变、下肢动脉病变、视力下降与行动不便，是足部问题的最高危人群，也最容易漏诊。

**为什么同时覆盖 1 型与 2 型？** 两型糖尿病都会并发周围神经病变与下肢动脉病变；国际风险分层标准（IWGDF 2023、新加坡 ACE 2024）对两型的足部风险判定一致。因此本项目的评估与分诊逻辑**不按糖尿病类型区分**，只要求「已确诊 1 型或 2 型」。

> **公平性说明：** 个人资料采集性别，但**不**用于筛选题目或加权 —— ACE 2024 / IWGDF 的风险分层并不按性别区分足部风险。这是刻意的公平性设计。

### 1.2 架构选型理由

| 决策                   | 理由                                                                                                         |
| -------------------- | ---------------------------------------------------------------------------------------------------------- |
| **PWA 而非原生 App**     | 无需应用商店审核周期（对黑客松速度至关重要）；iOS 和 Android 均可安装；通过 Service Worker 支持离线使用；单一代码库。                                  |
| **CloudBase 无服务器架构** | 零基础设施管理；自动扩缩容；内置认证、数据库、存储和静态托管；按量付费适合原型预算。                                                                 |
| **AI + 规则引擎混合架构**    | LLM 负责自然语言对话和多语言理解；确定性规则引擎执行严格的临床安全阈值。LLM 永远不对红旗症状做最终判定——规则引擎做。                                            |
| **专家包作为知识层**         | 糖尿病足临床逻辑（评估协议、预警阈值、就医路径、教育内容）被编码为 WorkBuddy 专家包。云函数从专家包中查询决策，而非在应用代码中硬编码临床逻辑。这类似于医学指南文档的工作方式——应用是载体，专家是协议。 |
| **单体仓库**             | 前端、云函数、共享类型、国际化和测试统一在单一仓库中。简化 CI/CD、版本管理和跨包重构。                                                             |
| **国际化优先，而非后期补丁**     | 五种语言从第一天起设计。ICU MessageFormat 处理各语言的复数、性别和数字格式。文化适配超越逐字翻译。                                                 |

### 1.4 八项必需能力

每项能力映射到架构中的特定组件：

#### 1.4.1 对话式评估

- **定义：** 基于聊天的界面，用户描述症状、回答问题，并获得初步足部风险评估。
- **实现方式：** 云函数 `assessment-engine` 编排多轮对话。它将用户消息 + 对话历史发送给 LLM，系统提示词以专家包的临床协议为基础。LLM 生成后续问题和结构化风险摘要。
- **安全护栏：** LLM 被指示永不做出诊断。它收集信息并分类风险；规则引擎产出最终风险等级。

#### 1.4.2 就医导航

- **定义：** 根据用户风险等级引导其采取适当的后续步骤——从"居家观察"到"两周内看足病医生"再到"立即前往急诊"。
- **实现方式：** 云函数 `care-navigator` 接收风险等级 + 用户上下文（位置、保险、偏好），返回带说明的优先级行动建议列表。导航内容通过国际化层进行本地化。

#### 1.4.3 预警信号检测

- **定义：** 识别需要立即就医的红旗症状（如可见溃疡、扩散性红肿、发热伴足部肿胀、黑色/焦炭样变色、突发剧烈疼痛、恶臭）。
- **实现方式：** 云函数 `warning-detector` 通过从专家包加载的确定性规则集处理用户回答。规则为简单的模式匹配：`IF symptom == "ulcer_open" THEN red_flag = true`。这有意不使用 AI——它必须可审计、可解释。

#### 1.4.4 安全拒答

- **定义：** 系统必须知道何时不应给出建议并转诊。当输入模糊、超出范围或提示紧急情况时，应用明确表示"我无法评估此情况——请联系医疗专业人士"并提供转诊路径。
- **实现方式：** 规则引擎包含一个拒答层。当置信度低于阈值、输入超出糖尿病足领域或任何红旗信号被触发时，系统拒答并转诊。LLM 也受到系统提示词约束，禁止虚构医疗指导。

#### 1.4.5 自我管理支持

- **定义：** 足部护理的教育内容和日常流程——每日检查、保湿（但趾间不涂）、合适鞋袜、趾甲护理、何时就医。
- **实现方式：** 从国际化层提供本地化的内容卡片（静态教育无需 LLM）。内容按风险等级分层——高风险用户获得更频繁的提醒和更详细的指导。包含简单的每日打卡（复选框式，非聊天，位于追踪页）以培养习惯。

#### 1.4.6 动态再评估

- **定义：** 风险不是静态的。系统定期提示用户重新评估（如每 30 天，或症状变化时更早）。历史评估被跟踪并呈现趋势。
- **实现方式：** 云函数 `reassessment-scheduler` 为每个用户存储 `nextAssessmentDue` 时间戳。应用打开时，如已过期则显示提示。趋势可视化显示风险随时间的变化。如果风险等级在评估间上升，系统主动转诊。

#### 1.4.7 个性化

- **定义：** 根据个体用户调整对话深度、内容复杂度、提醒频率和界面语言。
- **实现方式：** 云函数 `personalization-engine` 维护用户档案（年龄、糖尿病病程、合并症、首选语言、通过简短入门问卷评估的健康素养水平）。此档案作为上下文传递给评估引擎和就医导航器。个性化还影响 UI：健康素养较低 → 更简单的语言、更大的字体、更少的医学术语。

#### 1.4.8 子群公平性测试

- **定义：** 系统性测试以确保评估质量不会在特定人口或语言子群中下降。
- **实现方式：** 自定义基于 Jest 的测试框架运行合成用户角色的矩阵：
  - **语言：** EN, zh-CN, MS, TA, FIL
  - **年龄段：** 60–69, 70–79, 80–89, 大于 89
  - **性别：** 男, 女
  - **风险等级：** 低, 中, 高, 紧急
  - **健康素养：** 低, 中, 高
  - **输入风格：** 简练 vs. 详细，正式 vs. 口语  
    对于每个单元，框架运行完整评估流程并检查：(a) 风险等级分类正确，(b) 无不当医疗声明，(c) 适当的转诊，(d) 文化适宜的回应。生成公平性报告并提交至 `docs/fairness-report.md`。

### 1.6 专家包作为临床知识层

糖尿病足临床领域知识被结构化为 WorkBuddy 专家包。这个包不是 Web 应用本身——它是应用遵循的协议。包含：

| 组件           | 内容                                                                  |
| ------------ | ------------------------------------------------------------------- |
| **Agent 定义** | 角色：糖尿病足筛查助手。范围：非诊断性风险分层和教育。硬约束：永不诊断，始终听从执业医师。                       |
| **评估协议**     | 结构化决策树：初始症状采集 → 追问（神经病变症状、血管症状、视觉征象）→ 风险分层（低/中/高/紧急）。               |
| **预警信号规则**   | 确定性规则：开放性溃疡、扩散性红肿、发热 + 肿胀、黑色变色、恶臭、突发剧烈疼痛、足部失去知觉、可见骨/肌腱。每条规则映射到立即转诊。 |
| **就医路径**     | 风险等级 → 推荐行动映射（如低 → 自我护理 + 年度检查；高 → 两周内看足病医生；紧急 → 立即急诊）。             |
| **教育内容模板**   | 多语言足部护理教育模板，按风险等级和健康素养分层。                                           |
| **拒答标准**     | 系统必须拒绝评估并转诊的场景明确清单（模糊、超出范围、红旗、低置信度）。                                |

**为何用专家包而非硬编码规则？** 临床指南会变化。通过将协议外化为结构化、版本控制的专家包，我们可以在不触碰应用代码的情况下更新临床逻辑。这也使临床推理可审计——临床审核者可以阅读专家定义并与已发布指南（如 IWGDF——国际糖尿病足工作组）进行对照。

### 2.1 结构选型理由

| 选择                                         | 理由                                                        |
| ------------------------------------------ | --------------------------------------------------------- |
| **`apps/web` 与 `functions/` 分离**           | 前端和云函数有不同的构建流水线和部署目标。分离防止跨依赖泄漏到生产包中。                      |
| **`packages/shared`**                      | TypeScript 类型和验证 schema 被前端和云函数共用。workspace 包确保单一真相来源。    |
| **`packages/medical-rules`**               | 临床规则在云函数启动时从专家包加载。此包是将专家包 Markdown 翻译为 TypeScript 常量的适配器。 |
| **`expert-package/` 放在仓库中**                | 临床知识与代码一起版本管理。临床逻辑变更与代码变更走相同的 PR 审查流程。                    |
| **`docs/` 放在根目录**                          | 所有规划、架构和运营文档在此。演示脚本和设计权衡文档将在下一阶段添加。                       |
| **`.github/workflows/fairness-tests.yml`** | 公平性测试在每次 PR 上运行，而非仅在 main 分支。在合并前捕获子群性能回退。                |

## 3. 实施计划

计划组织为 **6 个阶段**，设计用于约 3 天的黑客松。每个阶段有明确的退出标准。如果进度超前，阶段可以压缩。

### 阶段 0：基础与脚手架（第 0–2 小时）

**目标：** 可用的单体仓库骨架 + CI 流水线。

| 任务                   | 详情                                                                           |
| -------------------- | ---------------------------------------------------------------------------- |
| 初始化单体仓库              | pnpm workspace + Turborepo 配置。根 `package.json` 包含共享脚本。                       |
| 搭建 `apps/web`        | `create-next-app` 使用 TypeScript、Tailwind、App Router。添加 `next-pwa`。           |
| 搭建 `packages/shared` | 共享类型：`User`、`Assessment`、`RiskTier`、`ConversationTurn`、`CareRecommendation`。 |
| 设置 i18n              | 安装 `react-i18next`。创建 5 个语言 JSON 文件，首页使用占位字符串。验证语言切换器工作。                     |
| CloudBase 项目设置       | 创建 TCB 环境（通过控制台，非代码）。编写 `cloudbaserc.json`。在测试云函数中初始化 JS SDK。                |
| GitHub Actions CI    | `ci.yml`：安装依赖 → 类型检查 → lint → 单元测试 → 构建。任何 PR 合并前必须通过。                       |
| 专家包脚手架               | 运行 `init_expert.py` 创建专家包骨架。填写 `plugin.json` 元数据。                            |

**退出标准：** `pnpm dev` 启动 Next.js 应用。语言切换器循环遍历全部 5 种语言。CI 流水线在简单 PR 上通过。

---

### 阶段 1：对话式评估 + 国际化（第 2–8 小时）

**目标：** 用户可以用 5 种语言中的任何一种进行多轮聊天对话讨论足部症状，并获得风险等级。

| 任务             | 详情                                                                                             |
| -------------- | ---------------------------------------------------------------------------------------------- |
| 构建聊天界面         | 消息列表、输入框、打字指示器、风险等级结果卡片。移动优先：全高聊天、拇指可达输入框。                                                     |
| 评估云函数          | `assessment-engine/index.ts`：接收用户消息 + 对话历史 + 用户档案。以专家包评估协议为基础的系统提示词调用 LLM。返回结构化响应（下一个问题或风险评估）。 |
| LLM 桥接         | `llm-bridge.ts`：封装 LLM API 调用。包括：指数退避重试、8 秒超时、优雅回退（LLM 失败时显示静态问卷而非崩溃）。                         |
| 风险分层逻辑         | `packages/medical-rules/risk-stratification.ts`：接收结构化对话输出 → 基于专家包阈值计算风险等级（低/中/高/紧急）。           |
| 评估的 i18n 内容    | 将所有 UI 字符串、风险等级标签、说明文本翻译为全部 5 种语言。不是逐字翻译——将临床术语适配为各语言环境中通俗易懂的表达。                               |
| 编写专家包 Agent MD | 完整临床协议：症状采集问题、追问逻辑、风险阈值、范围约束、拒答触发条件。                                                           |
| 单元测试           | 用覆盖全部 4 个风险等级的合成对话输出测试风险分层。测试所有语言环境的 i18n key 完整性。                                             |

**退出标准：** 用户可以打开应用、选择语言、聊天讨论足部症状并看到风险等级结果。所有 UI 文本已本地化。

---

### 阶段 2：预警信号检测 + 安全拒答（第 8–14 小时）

**目标：** 系统检测红旗症状并在适当时拒答。

| 任务          | 详情                                                                                                                        |
| ----------- | ------------------------------------------------------------------------------------------------------------------------- |
| 预警信号规则引擎    | `warning-detector/index.ts` + `rules.ts`：从 `packages/medical-rules/warning-signs.ts` 加载的确定性规则。在每条用户消息上运行。如规则触发，立即中断对话并转诊。 |
| 拒答层         | 如果输入超出范围（如用户询问心脏病）、低置信度（LLM 不确定度超阈值）或触发红旗——系统明确表示"我无法评估此情况"并提供转诊指导。这是 LLM 系统提示词中的硬约束，同时由后处理规则强制执行。                        |
| 转诊界面        | 红色横幅显示立即行动步骤。电话号码/急诊方向（已本地化）。"立即联系您的医疗服务提供者"，移动端支持点击拨打。                                                                   |
| 专家包中的预警信号目录 | `references/warning-signs.md`：完整的红旗症状目录，含临床理据和转诊紧急程度（立即 vs. 24 小时 vs. 1 周）。                                               |
| 单元 + 集成测试   | 测试每条预警信号规则正确触发。测试超出范围查询的拒答。测试红旗转诊中断对话。                                                                                    |

**退出标准：** 当用户提到开放性溃疡或扩散性红肿时，系统立即转诊。当用户询问非足部医疗问题时，系统拒答。两种行为均已测试。

### 阶段 3：就医导航 + 自我管理（第 14–20 小时）

**目标：** 用户获得可操作的就医建议和教育内容。

| 任务                | 详情                                                                                               |
| ----------------- | ------------------------------------------------------------------------------------------------ |
| 就医导航器函数           | `care-navigator/index.ts`：接收风险等级 + 用户上下文 → 返回优先级建议。如中度风险 → "两周内预约足病医生" + "开始每日足部检查（见下方指南）"。      |
| 就医路径定义            | `packages/medical-rules/care-pathways.ts` + 专家包 `references/care-pathways.md`：风险等级 → 行动映射，含紧急程度。 |
| 教育内容库界面           | 卡片式内容浏览器。内容按类别组织（日常护理、鞋袜、趾甲护理、何时就医）。按风险等级筛选。                                                     |
| 每日打卡              | 简单表单："今天检查了脚吗？" + "有何变化？" + 可选照片。连续打卡追踪。推送通知调度（通过 CloudBase 定时函数）。                               |
| 教育内容              | 编写并翻译全部 5 种语言的足部护理教育内容。按风险等级分层（低风险用户获得基础知识；高风险用户获得详细的溃疡预防、减压指导）。                                 |
| 端到端测试（Playwright） | 完整旅程：入门引导 → 评估 → 获得风险 → 查看建议 → 阅读教育内容 → 完成每日打卡。用英文和至少一种其他语言。                                     |

**退出标准：** 评估后，用户看到量身定制的就医建议和相关教育内容。每日打卡功能可用。端到端测试在 2 种语言中通过。

### 阶段 4：动态再评估 + 个性化（第 20–26 小时）

**目标：** 系统随时间适应并个性化体验。

| 任务          | 详情                                                                                                                       |
| ----------- | ------------------------------------------------------------------------------------------------------------------------ |
| 再评估调度器      | `reassessment-scheduler/index.ts`：基于当前风险等级计算 `nextAssessmentDue`（低 → 90 天，中 → 30 天，高 → 14 天，紧急 → 不适用，已转诊）。应用打开时如已过期显示提示。 |
| 趋势可视化       | 折线图显示风险等级随时间变化（使用轻量图表库——如 `recharts` 或自定义 SVG）。颜色编码：绿=低，琥珀=中，红=高，深红=紧急。                                                  |
| 个性化引擎       | `personalization-engine/index.ts`：接收用户档案 → 生成个性化上下文（语言复杂度级别、UI 字体大小偏好、提醒频率、对话深度）。传递给评估引擎和就医导航器。                          |
| 入门问卷        | 简短（5–7 个问题）入门：年龄、糖尿病病程、合并症、健康素养自评、首选语言。为个性化引擎提供数据。                                                                       |
| 档案驱动的 UI 适配 | 如果健康素养为"低"，简化就医建议中的语言（更短的句子、更少的医学术语、更多类比）。如果年龄 > 65，默认使用更大字体。                                                            |
| 单元测试        | 测试再评估调度逻辑。测试边界情况的个性化上下文生成。                                                                                               |

**退出标准：** 不同档案的用户获得明显不同的体验。再评估提示按时出现。趋势图使用模拟历史数据正确渲染。

## 4. 风险与缓解措施

### 4.1 临床安全风险

| 风险             | 严重程度  | 描述                                  | 缓解措施                                                                                                     |
| -------------- | ----- | ----------------------------------- | -------------------------------------------------------------------------------------------------------- |
| **红旗症状假阴性**    | 🔴 严重 | 系统未能检测到预警信号（如用户用口语描述溃疡，LLM 未识别为红旗）。 | (1) 规则引擎在每条消息上运行，而非仅最终评估。(2) 规则包含每种语言中症状的口语/俚语表达。(3) 置信度 < 阈值时系统拒答并转诊。(4) 显著免责声明："本工具不替代专业医疗评估。"         |
| **LLM 虚构医疗建议** | 🔴 严重 | LLM 生成协议中不存在的具体治疗建议或诊断。             | (1) 系统提示词有硬约束："永不诊断。永不开具治疗。永不违背已确立的临床指南。"(2) 后处理过滤器扫描 LLM 输出中的禁止模式（"诊断"、"开具"、"你有"、"服药"）。(3) 过滤器触发时回退到拒答。 |
| **用户过度依赖工具**   | 🟠 高  | 用户将应用视为专业护理的替代品，延迟就医。               | (1) 在关键时刻（评估后、教育内容中）重复免责声明。(2) 中度及以上风险的建议始终包含专业随访。(3) 再评估提示强化"这是监测，不是诊断"。                                |
| **风险等级误分类**    | 🟠 高  | 风险分层产生的等级低于应有水平。                    | (1) 保守阈值——有疑虑时向上分级，不向下。(2) 专家包阈值对照 IWGDF 指南审查。(3) 公平性测试包含等级边界的边缘案例。                                      |

### 4.2 技术风险

| 风险                  | 严重程度 | 描述                                                  | 缓解措施                                                                                                           |
| ------------------- | ---- | --------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| **LLM 延迟/不可用**      | 🟠 高 | 对话评估依赖 LLM 调用，可能缓慢（>5 秒）或完全失败。                      | (1) 每次 LLM 调用 8 秒超时。(2) 优雅回退：LLM 失败时切换到静态决策树问卷（预定义问题，无自然语言）。(3) 加载状态 + "正在处理"消息。(4) 在函数中缓存评估协议以避免重复获取。         |
| **5 种语言的 i18n 质量**  | 🟠 高 | 翻译质量参差不齐；临床术语在 Tamil 或 Filipino 中可能没有直接对应词。         | (1) 邀请母语者审查医学术语（即使黑客松期间仅抽查）。(2) 在临床术语旁使用通俗语言描述。(3) 公平性测试捕获语言特有的分类失败。(4) ICU MessageFormat 处理语法差异。              |
| **CloudBase 冷启动延迟** | 🟡 中 | 无服务器云函数首次调用时可能有冷启动延迟（1–3 秒）。                        | (1) 保持函数轻量——在模块作用域加载专家包规则，而非每次调用。(2) 如需可考虑预热 ping。(3) 前端在函数调用期间显示骨架屏。                                          |
| **离线模式限制**          | 🟡 中 | PWA Service Worker 缓存静态资源，但评估需要实时 LLM 调用。           | (1) 离线模式显示缓存的教育内容 + 每日打卡（回到线上时同步）。(2) 明确提示："评估需要网络连接。"(3) 打卡数据排队等待同步。                                          |
| **单体仓库构建复杂性**       | 🟡 中 | Turborepo + pnpm workspaces + Next.js + 云函数可能有配置摩擦。 | (1) 保持依赖图简单——`packages/shared` 是唯一的跨边界依赖。(2) Turborepo 处理缓存；如有缓存问题，`--force` 标志可绕过。(3) web 和 functions 分离构建配置。 |


### 4.3 公平性与偏差风险

| 风险                    | 严重程度  | 描述                                                | 缓解措施                                                                                                                |
| --------------------- | ----- | ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| **基于语言的性能差异**         | 🔴 严重 | LLM 在英语中可能比 Tamil 或 Filipino 表现更好，导致非英语用户的风险分类更差。 | (1) 公平性测试矩阵明确测试全部 5 种语言。(2) 如发现差异，调查是 LLM 能力还是 i18n 质量问题。(3) 对于 LLM 较弱的语言，增加更多确定性规则检查来补偿。(4) 在公平性报告中公开所有差异——透明而非隐瞒。 |
| **年龄段偏差**             | 🟠 高  | 60 岁以上的用户群体内部差异很大（60 多岁与 80 岁以上在技术素养、健康素养、视力、行动力上差别明显）。高龄用户可能给出更简短、更少结构化的输入。 | (1) 公平性测试覆盖全部 4 个年龄段（60–69 / 70–79 / 80–89 / 大于 89）并包含"简短输入"角色。(2) 评估协议有自适应追问——如果初始输入稀疏，提出更多后续问题而非猜测。(3) UI 默认 18px 基础字号、44px 触控目标、高对比度，适配视力与行动不便。 |
| **临床阈值中的性别偏差**        | 🟡 中  | 某些糖尿病足风险因素在不同性别中表现不同（如外周动脉疾病患病率）。                 | (1) 专家包在指南不同时引用性别感知阈值。(2) 公平性测试将性别作为维度。(3) 如数据不足，统一使用保守（更低）阈值。                                                      |
| **就医导航中的文化偏差**        | 🟡 中  | 就医建议可能假设不同地区有不同的医疗基础设施（如"看足病医生"在农村地区可能不可行）。       | (1) 就医路径包含回退选项（"如无足病医生，看全科医生"）。(2) 本地化超越翻译——尽可能适应当地医疗环境。(3) 用户入门采集位置信息用于导航上下文。                                      |
| **输入风格偏差（正式 vs. 口语）** | 🟡 中  | 正规教育程度较低的用户可能用非临床语言描述症状，LLM 可能解读不同。               | (1) 专家包包含每种语言的口语症状描述。(2) 公平性测试包含"口语"输入风格角色。(3) 规则引擎匹配通俗用语，而非仅临床术语。                                                  |

### 4.4 监管与合规风险

| 风险               | 严重程度  | 描述                                       | 缓解措施                                                                                                              |
| ---------------- | ----- | ---------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| **医疗器械监管**       | 🔴 严重 | 根据司法管辖区，对医疗状况进行风险分层的工具可能被归类为需要监管批准的医疗器械。 | (1) **明确定位：** 应用是"筛查和教育工具"，**不是**诊断设备。所有输出均为"初步风险指标"而非诊断。(2) 全程显著免责声明。(3) 黑客松原型明确标注为"原型，非临床使用"。(4) 任何生产部署前咨询监管专家。 |
| **数据隐私（用户健康数据）** | 🟠 高  | 应用收集健康信息（症状、风险评估、每日打卡），属于敏感个人数据。         | (1) CloudBase 认证 + 数据库安全规则实现按用户数据隔离。(2) 数据最小化——仅采集评估所需数据。(3) 清晰的隐私政策。(4) 用户可导出和删除其数据。(5) 健康数据不发送至第三方分析。           |
| **LLM 数据处理**     | 🟠 高  | 如使用第三方 LLM API，用户对话数据可能被 LLM 提供方处理。      | (1) 尽可能使用 WorkBuddy 的托管 LLM 端点（无独立提供方）。(2) 如使用外部 API，在发送给 LLM 前脱敏 PII。(3) 在信任边界图中记录数据流。(4) 检查提供方的数据留存政策。          |

### 4.5 运营风险

| --------------------- | ---- | ------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| **黑客松时间约束**           | 🟠 高 | 在黑客松时间框架内完成 8 项能力 + 5 种语言 + 公平性测试 + 4 份交付物是雄心勃勃的。 | (1) 分阶段计划有明确退出标准——如进度落后，阶段 5（公平性）可使用精简角色矩阵。(2) 优先级：评估 + 预警检测 + 拒答不可妥协；其他可以更薄。(3) 为演示预置测试数据以避免实时数据问题。   |
| **CloudBase 账户/配额限制** | 🟡 中 | 免费层或黑客松额度可能对函数调用或数据库有限制。                          | (1) 在 CloudBase 控制台监控用量。(2) 积极缓存——专家包规则每次冷启动加载一次。(3) 开发/测试时使用模拟 LLM 响应以节省 API 调用。                      |
| **单体仓库中的团队协作**        | 🟡 中 | 多人在单体仓库中工作可能导致合并冲突和构建中断。                          | (1) 明确的目录归属（前端人员负责 `apps/web`，后端人员负责 `functions/`）。(2) `packages/shared` 变更需要双方 PR 审查。(3) CI 捕获跨包类型错误。 |
